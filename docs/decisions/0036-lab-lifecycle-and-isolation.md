# Architecture Decision Record (ADR) 0036: Practice Lab Lifecycle and Isolation

## Status
Accepted

## Context
Milestone 13 introduces an isolated practice lab allowing operators, security practitioners, and defensive engineers to reproduce and troubleshoot common network connectivity failures and defensive audit findings locally without requiring paid services, cloud infrastructure, or contacting public targets.

Phase 13.1 defines the architectural foundation for practice lab lifecycle, state persistence, service binding boundaries, and safety containment:
1. **Repeatable Lifecycle:** Lab setup, reset, and teardown must be fully deterministic and repeatable across arbitrary executions.
2. **Strict Loopback Binding:** Lab services must bind strictly to loopback addresses (`127.0.0.1` or `::1`) by default, utilizing ephemeral ports or explicitly designated local ports. Any attempt to bind to wildcard (`0.0.0.0`) or external network interfaces must be strictly rejected.
3. **Safety Containment and Non-Destructive Cleanup:** Cleanup and reset operations must be sandboxed strictly to WireScope lab-owned resources and files under `<data_dir>/lab/`. Path traversal (`..`) or unauthorized file modifications outside the sandbox must be rejected. Cleanup must never terminate unrelated host processes.
4. **Synthetic Data Distinguishability:** All lab scenarios, observations, reports, and verification outputs must be unambiguously labeled with synthetic metadata badges (`[SYNTHETIC_LAB_FIXTURE]`), provenance strings (`synthetic_lab_fixture`), and origin notices to prevent accidental confusion with live network assessments.
5. **Target Confinement:** Lab execution must never silently query public internet targets. All scenario targets must be confined to loopback addresses or RFC 6761 / RFC 2606 reserved testing domains (`.test`, `.example`, `.invalid`, `.localhost`).

## Decision

### 1. Versioned Scenario Model (`src/lab/scenario.zig`)
The scenario architecture is codified under versioned schema `LAB_SCENARIO_SCHEMA_VERSION = 1`. Each scenario defines:
- `id` and `id_str`: Canonical identifier (e.g. `dns_failure`, `tcp_refusal_timeout`, `tls_cert_issues`, `unexpected_listener`, `http_security_header_violation`, `remediation_verification`).
- `title`, `category`, and `difficulty`: Metadata for human operator navigation.
- `objective` and `description`: Technical explanation of the learning and diagnostic goals.
- `instructions` and `hints`: Actionable step-by-step guidance.
- `expected_observations`: Structured criteria detailing expected failure codes, findings, and targets.
- `verification_steps` and `cleanup_strategy`: Criteria for evaluating operator remediation and teardown procedures.
- `is_synthetic = true`: Explicit boolean stamp included in all serialization formats.

### 2. Controlled Loopback Service (`src/lab/service.zig`)
The `LabLoopbackService` manages controlled TCP and mock HTTP services:
- Binds strictly to `127.0.0.1` or `::1`. Rejects non-loopback IPs with `error.NonLoopbackBindForbidden`.
- Supports ephemeral port allocation (`port = 0`), retrieving kernel-assigned ports via cross-platform `getsockname`.
- Implements polling-based non-blocking accept loops (`select` on Windows, `poll` on POSIX) with atomic `should_stop` flags to achieve immediate, leak-free shutdowns without socket race conditions.
- Uses dedicated `sendBytes` and `recvBytes` helpers linking directly to `ws2_32.dll` on Windows to avoid external libc dependencies.

### 3. Sandbox Containment and Lifecycle Manager (`src/lab/manager.zig`)
The `LabManager` governs scenario state and sandbox integrity:
- Manages active state in `<data_dir>/lab/active_state.json` using atomic write patterns.
- Validates all file targets against directory traversal attacks via `validateSandboxPath`. Any relative (`..`), absolute (`/`, `C:\`), or prefixed paths outside the lab sandbox return `error.SandboxEscapeDetected`.
- Cleanup removes only verified lab-owned files and safely terminates only the managed loopback services.
- Repeatable lifecycle: setup -> inspect -> status -> reset -> cleanup -> setup executes deterministically with zero memory or socket leaks.

### 4. Synthetic Provenance Enforcement (`src/lab/synthetic.zig`)
WireScope strictly tags all lab operations:
- `SYNTHETIC_DATA_BADGE`: `"[SYNTHETIC_LAB_FIXTURE]"` prominently displayed on all CLI and markdown outputs.
- `SYNTHETIC_PROVENANCE`: `"synthetic_lab_fixture"` serialized in all JSON records.
- `SYNTHETIC_ORIGIN_NOTICE`: Clarifies that observations are generated by isolated local fixtures.
- Target confinement: `validateLabTarget` enforces that all lab commands target only loopback or RFC 6761 reserved domains, returning `error.PublicTargetForbiddenInLab` for external domains or IPs.

### 5. CLI Integration (`src/cli/root.zig`)
Exposes dedicated subcommands under `wirescope lab`:
- `wirescope lab list`: Catalogs exercises across terminal, JSON, and Markdown formats.
- `wirescope lab inspect <id>`: Displays comprehensive exercise objectives, instructions, and hints.
- `wirescope lab setup <id>` / `run <id>`: Initializes scenario state and activates loopback listeners.
- `wirescope lab status`: Reports active scenario, assigned port, and target configuration.
- `wirescope lab verify <id>`: Evaluates diagnostic evidence against scenario criteria.
- `wirescope lab reset`: Restores initial clean scenario state.
- `wirescope lab cleanup`: Shuts down active listeners and purges temporary lab artifacts.

## Consequences

### Positive
- Practice exercises execute 100% locally with zero internet access, cloud infrastructure, or paid APIs.
- Strict sandbox containment guarantees that reset and cleanup cannot modify or delete arbitrary host files.
- Loopback isolation ensures no risk of unexpected network exposure during training.
- Complete distinguishability between lab fixtures and live assessment data.

### Neutral / Trade-offs
- Lab services must use available local loopback ports; ephemeral port allocation avoids port collisions on development machines.
