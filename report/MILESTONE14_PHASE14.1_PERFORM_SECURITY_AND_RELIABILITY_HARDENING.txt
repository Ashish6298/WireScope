2. HARDENING & PROPERTY FUZZING ENGINE (`src/core/hardening.zig`)
--------------------------------------------------------------------------------
A dedicated hardening module and PRNG-driven property fuzzing engine was built to
stress-test parsing and security boundaries across 5 key input vectors:

1. Hostname Normalization Fuzzing (`fuzzHostnames`):
   - Generates >253-character FQDNs, >63-character labels, control characters
     (0x00-0x1F), whitespace, null bytes, punctuation (`/`, `\`, `@`, `!`, `?`),
     leading/trailing hyphens (`-test.com`, `test-.com`), and consecutive dots (`..`).
   - Invariant: Rejects malformed strings returning `error.MalformedHostname` or
     `error.EmptyTargetString` safely without panic or memory leaks.

2. IPv4 Address Fuzzing (`fuzzIpv4`):
   - Generates overflow octets (>255), negative numbers, non-numeric octets (`abc`),
     incorrect octet counts (<4 or >4), leading zeros, and trailing dots.
   - Invariant: Safely rejects with `error.MalformedIpAddress` without memory leaks.

3. Port Specification Fuzzing (`fuzzPorts`):
   - Generates port 0, ports >65535, inverted ranges (`8080-80`), malformed delimiters
     (`80--443`), non-numeric inputs, and port sets exceeding configured safety caps.
   - Invariant: Safely rejects with `error.InvalidPortSyntax`, `error.InvalidPortRange`,
     or `error.ExcessivePortCount`.

4. Sandbox Path Traversal Fuzzing (`fuzzSandboxPaths`):
   - Generates path traversal sequences (`../`, `..\`, `foo/../../bar`), root paths
     (`/etc/passwd`, `C:\Windows\System32`), UNC paths (`\\server\share`), colons,
     and null bytes.
   - Invariant: Safely rejects with `StorageError.PathTraversalEscape`.

5. JSON Envelope Fuzzing:
   - Evaluates empty strings, truncated structures, missing mandatory envelope keys,
     unexpected field types, and unauthorized secret keys (`"private_key"`).
   - Invariant: Safely rejects with typed `SchemaValidationError` without crashing.

3. SCOPE-ESCAPE REGRESSION SUITE
--------------------------------------------------------------------------------
WireScope enforces strict multi-layered defenses preventing any scan or audit from
escaping approved operator scope:

- DNS Rebinding Prevention:
  * Invariant: `verifyDnsScopeCompliance` verifies that if a loopback target
    (`localhost`) resolves to a public or remote IP (e.g. `8.8.8.8`), the operation
    is halted immediately with `error.ScopeExpansionPrevented`.
- Target Exclusion Precedence:
  * Invariant: Exclusions strictly override included scopes. If a resolved IP
    matches an explicit exclusion entry, it is halted with `error.ResolvedTargetExcluded`.
- HTTP Redirection Scope Guard:
  * Invariant: HTTP probes default to `allow_redirect_scope_expansion: false`.
    Redirects that target unapproved external domains or foreign hosts are blocked
    pre-connection and recorded as `WS-AUDIT-HTTP-REDIRECT-SCOPE`.
- Redirection Hop Caps:
  * Invariant: Redirection chains are capped at `max_redirects: 5` to prevent infinite
    redirect loops or resource exhaustion attacks.
- Broad CIDR Rejection:
  * Invariant: Network prefixes broader than `/24` (e.g. `/16`, `/8`) are rejected
    by default with `error.ExcessiveCidrRange`.

4. RESOURCE BOUNDS, CANCELLATION, AND CLEANUP
--------------------------------------------------------------------------------
- Response Buffer Limits:
  * HTTP response bodies are limited to `max_response_bytes: 1MB`, preventing heap
    exhaustion from maliciously oversized HTTP streams.
- Cooperative Cancellation:
  * Thread-safe `CancellationToken` is checked at every probe dispatch and loop
    iteration. Cancelling cleanly stops probe batches, immediately closing all open
    sockets and deallocating memory with zero leaks.
- Interrupted Atomic Writes:
  * Files are written via the write-to-temp-then-atomic-rename pattern (`atomicWriteFile`).
    If a write is interrupted, aborted, or fails, the temporary `.tmp.{timestamp}` file
    is unlinked via `defer`, guaranteeing that target destination files are never
    corrupted or partially written.
- Report Redaction:
  * Sensitive Authorization headers (Bearer, Basic), API keys, and passwords in URLs
    are deterministically masked as `[REDACTED]` prior to serialization.

5. AUTHORITATIVE RESIDUAL RISKS CATALOG
--------------------------------------------------------------------------------
In accordance with defensive honesty and engineering transparency, WireScope formally
catalogs residual risks in `src/core/hardening.zig` (`RESIDUAL_RISKS`) and in
`docs/security_hardening_and_residual_risks.md`:

1. DNS Rebinding Window (TOCTOU):
   - Mechanism: Authoritative DNS servers could return a loopback IP during initial
     pre-flight scope verification, and return a remote IP during socket connect.
   - Defense: WireScope re-verifies resolved IPs immediately prior to socket connect.
   - Residual Limitation: OS resolver cache timing could permit a narrow TOCTOU race.
   - Recommendation: Pin static IP addresses or use local `/etc/hosts` mappings.

2. OS Privilege Boundaries for Process Attribution:
   - Mechanism: Correlating local listening sockets with owning process names/PIDs
     requires administrative/root privileges on Windows and Linux.
   - Defense: WireScope enumerates listeners accurately and flags missing process info.
   - Residual Limitation: Unprivileged execution cannot attribute processes, emitting
     `WS-AUDIT-EXPOSURE-PERMISSION-LIMITED`.
   - Recommendation: Run with elevated privileges when process attribution is required.

3. Host System Clock Reliance:
   - Mechanism: Certificate expiration checks rely on local host clock time.
   - Defense: Deterministic date window calculations.
   - Residual Limitation: Skewed host clocks cause false positive/negative expirations.
   - Recommendation: Ensure NTP/PTP synchronization on assessment hosts.

4. Stateful Firewall & Middlebox Interference:
   - Mechanism: Intermediate firewalls can inject TCP RST packets or silently drop probes.
   - Defense: Millisecond-precision latency measurements and multi-hypothesis findings.
   - Residual Limitation: Cannot distinguish true destination rejection from middlebox RST
     without packet captures on the target endpoint.
   - Recommendation: Verify connectivity from multiple vantage points and check firewall logs.

5. Local Filesystem Access Controls:
   - Mechanism: Saved history, profiles, and manifests rely on OS user permissions.
   - Defense: WireScope uses per-user application directories and enforces sandbox containment.
   - Residual Limitation: Other processes under the same user account have read access.
   - Recommendation: Maintain user account isolation and utilize full disk encryption.

6. Local Hash Integrity vs Authenticity:
   - Mechanism: SHA-256 manifests detect accidental corruption or modification.
   - Defense: Versioned SHA-256 manifests across all report artifacts.
   - Residual Limitation: Local hashes cannot prove author identity or prevent tampering
     by an attacker with write access to both report and manifest.
   - Recommendation: For cryptographic authenticity, sign manifests with external GPG/Sigstore.
